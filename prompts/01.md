# 01 — Plano de Execução para o Modelo Opus (Antigravity)

> **Para o modelo:** este é o seu plano de execução completo do projeto **Be4Hope**.
> Antes de qualquer ação, leia obrigatoriamente `CLAUDE.md` e `AGENTS.md` na raiz do repositório.
> Toda regra de negócio, escopo de tela e padrão técnico já está documentado lá — **não duplique**, apenas implemente.
> Este arquivo (`01.md`) é a **ordem cronológica** que você deve seguir, fase por fase, sem pular etapas.

---

## Regras de operação inegociáveis

1. **Trabalhe fase a fase.** Só inicie a próxima fase quando a anterior estiver com o **Definition of Done** marcado.
2. **Ao final de cada fase**, rode `pnpm lint` e `pnpm build` — só prossiga se ambos passarem.
3. **Commits pequenos e nomeados** no padrão `feat(fase-X): <descrição>` ou `chore(fase-X): <descrição>`.
4. **Nunca crie componente visual do zero** se existir equivalente shadcn/ui. Adicione via `pnpm dlx shadcn@latest add <comp>`.
5. **Versões amarradas sempre** — sem `^` nem `~` no `package.json`.
6. **Pare e pergunte** ao humano somente nos pontos marcados com 🛑 neste arquivo. Em todo o resto, prossiga sem pedir confirmação.
7. **Consulte o Context7** sempre que houver dúvida de API atualizada do Next.js, Drizzle, Clerk ou qualquer lib citada.
8. **Idioma:** todo o código, UI, mensagens, e-mails e comentários em **PT-BR**.
9. **Após cada fase**, atualize `/docs/progresso.md` marcando a fase como concluída e listando arquivos criados.

## Fase 1 — Fundação do projeto

**Objetivo:** projeto Next.js inicializado, autenticação funcional, shadcn pronto.

**Passo a passo:**

1. Inicialize o projeto na raiz:
   ```bash
   pnpm create next-app@latest . --ts --eslint --tailwind --app --src-dir=false --import-alias="@/*"
   ```
2. Configure `pnpm-workspace.yaml` se necessário e adicione `.npmrc` com `engine-strict=true`.
3. Instale ferramentas de qualidade com versões amarradas:
   ```bash
   pnpm add -D prettier prettier-plugin-tailwindcss @types/node
   ```
4. Crie `.prettierrc`, `.prettierignore` e ajuste o `eslint.config` para integrar com Prettier.
5. Configure scripts no `package.json`:
   - `dev`, `build`, `start`, `lint`, `format`, `db:generate`, `db:migrate`, `db:studio`
6. Instale e configure **shadcn/ui**:
   ```bash
   pnpm dlx shadcn@latest init
   ```
   Tema: **slate** ou **zinc**, com suporte a dark mode. Pasta de componentes: `/components/ui`.
7. Adicione os componentes shadcn essenciais de partida:
   `button`, `input`, `label`, `form`, `card`, `dialog`, `dropdown-menu`, `sheet`, `tabs`, `table`, `toast`, `sonner`, `avatar`, `badge`, `separator`, `select`, `textarea`, `calendar`, `popover`, `tooltip`, `skeleton`, `alert`, `alert-dialog`, `navigation-menu`.
8. Instale **Drizzle + Neon**:
   ```bash
   pnpm add drizzle-orm @neondatabase/serverless
   pnpm add -D drizzle-kit
   ```
9. Crie `/lib/db/index.ts` com cliente Neon + Drizzle.
10. Crie `drizzle.config.ts` apontando para `/db/schema` e `/db/migrations`.
11. Instale e configure **autenticação**. Padrão recomendado: **Clerk** (UI pronta, rápido).
    - Caso o humano tenha pedido NextAuth, troque aqui.
    - Configure os 3 roles via `publicMetadata.role`: `admin`, `medico`, `paciente`.
12. Crie middleware de proteção de rotas em `middleware.ts`.
13. Crie `/lib/env.ts` com validação **Zod** de todas as variáveis de ambiente.
14. Crie `.env.example` com **todas** as variáveis (sem valores reais).
15. Crie estrutura de pastas conforme `CLAUDE.md`:
    ```
    /app/(public) /app/(auth) /app/(medico) /app/(paciente) /app/(admin)
    /components/shared /components/forms
    /lib/integrations /lib/auth /lib/utils
    /db/schema /db/migrations
    /docs
    ```
16. Adicione um layout raiz com **Providers** (Theme, Toaster, Auth).
17. Página inicial temporária só com "Be4Hope" e link de login para validar o boot.
18. Rode `pnpm dev` e confirme: home renderiza, `/sign-in` abre, login com role grava metadata, redireciono pós-login funciona conforme role.

**Definition of Done:**
- [ ] `pnpm dev` sobe sem erros
- [ ] shadcn instalado, componentes-base adicionados
- [ ] Drizzle conectado ao Neon (sem schema ainda)
- [ ] Login funcional com 3 roles e redirecionamento
- [ ] `/lib/env.ts` validando variáveis
- [ ] Estrutura de pastas criada
- [ ] Commit: `feat(fase-1): fundação do projeto`

## Fase 2 — Modelagem do banco

**Objetivo:** schema completo no Drizzle, migrations aplicadas no Neon.

**Padrões obrigatórios:**
- Toda tabela: `id` (CUID via `createId()`), `created_at`, `updated_at`
- Soft delete (`deleted_at`) onde fizer sentido clínico
- Drizzle `relations()` declaradas para cada vínculo
- Enums declarados em arquivo próprio `/db/schema/enums.ts`

**Ordem das tabelas (criar exatamente nesta ordem):**

1. **enums** — `user_role`, `paciente_status`, `tratamento_tipo`, `documento_tipo`, `consulta_status`, `notificacao_tipo`
2. **users** — id, email, nome, role, telefone, avatar_url, timestamps
3. **medicos** — user_id (FK), crm, especialidade, bio, google_calendar_id, google_refresh_token (criptografado)
4. **pacientes** — user_id (FK), medico_id (FK), data_nascimento, cpf, responsavel_nome (se menor), responsavel_cpf, status, tratamento_tipo, endereco
5. **triagens** — id, dados (JSONB com todas as respostas), email_contato, telefone_contato, status_visualizacao
6. **documentos** — paciente_id (FK), tipo, url_blob, data_emissao, data_validade, observacoes
7. **consultas** — paciente_id (FK), medico_id (FK), data_hora, status, google_event_id, google_meet_link, observacoes
8. **anamneses** — paciente_id (FK), conteudo (rich text), criado_por (medico_id)
9. **evolucoes** — paciente_id (FK), data, conteudo, nivel_dor (0-10), qualidade_sono (0-10), bem_estar (0-10), criado_por
10. **medicamentos** — id, nome, principio_ativo, gotas_por_ml (default 20)
11. **dosagens** — paciente_id (FK), medicamento_id (FK), gotas_por_dia, ml_frasco, data_inicio, data_fim_prevista, ativa
12. **recompras** — dosagem_id (FK), data_prevista, status (`agendada`, `pedida`, `entregue`), email_enviado_em
13. **grupos_chat** — id, nome, criado_por, tipo (`direto`, `grupo`)
14. **participantes_grupo** — grupo_id, user_id
15. **mensagens** — grupo_id, autor_id, conteudo, lida_por (JSONB array)
16. **notificacoes** — user_id, tipo, titulo, mensagem, lida, link_acao
17. **logs_auditoria** — user_id, acao, entidade, entidade_id, dados_antes (JSONB), dados_depois (JSONB), ip

**Ações:**
1. Crie cada arquivo em `/db/schema/<entidade>.ts`.
2. Crie `/db/schema/index.ts` reexportando tudo.
3. Crie helper `/db/schema/_helpers.ts` com colunas comuns (`id`, `timestamps`).
4. Rode `pnpm db:generate` e revise a migration gerada.
5. Rode `pnpm db:migrate` (no banco de **desenvolvimento** do Neon).
6. Abra `pnpm db:studio` e confirme que todas as tabelas existem.
7. Crie `/db/seed.ts` com dados mínimos para dev: 1 admin, 2 médicos, 3 pacientes, 5 medicamentos, 1 grupo de chat. Execute uma vez.

**Definition of Done:**
- [ ] Todas as 17 tabelas/enums criados
- [ ] Migration aplicada com sucesso no Neon dev
- [ ] Drizzle Studio mostra tudo
- [ ] Seed funcional executado
- [ ] Commit: `feat(fase-2): schema completo do banco`

## Fase 4 — Server Actions e regras de negócio

**Objetivo:** toda regra de negócio do `CLAUDE.md` implementada em Server Actions, com validação Zod e checagem de role.

**Padrão de cada action:**
```ts
"use server";
// 1. Validar entrada com Zod
// 2. Verificar usuário autenticado e role
// 3. Verificar permissão sobre o recurso (médico só mexe nos próprios pacientes etc.)
// 4. Executar lógica (DB + integrações)
// 5. Registrar em logs_auditoria quando for dado clínico
// 6. revalidatePath/revalidateTag conforme necessário
// 7. Retornar { ok, data } | { ok: false, erro }
```

**Helpers a criar primeiro:**
- `/lib/auth/get-current-user.ts`
- `/lib/auth/require-role.ts`
- `/lib/auth/require-paciente-do-medico.ts`
- `/lib/utils/dosagem.ts` — funções puras: `calcularDataFimPrevista`, `calcularDataNotificacaoRecompra`
- `/lib/utils/documento.ts` — `calcularDataValidade(tipo, dataEmissao)` (Anvisa 24m, Receita 6m)
- `/lib/utils/audit.ts` — `registrarAuditoria(...)`

**Actions a implementar (agrupadas por feature):**

1. **Triagem pública**
   - `enviarTriagem(dados)`

2. **Pacientes**
   - `criarPaciente`, `atualizarPaciente`, `arquivarPaciente`, `importarPacientesCSV`

3. **Documentos**
   - `uploadDocumentoPaciente` (calcula validade automaticamente)
   - `removerDocumento`

4. **Consultas / Agendamento**
   - `listarHorariosDisponiveis(medicoId, data)`
   - `agendarConsulta` — orquestra: cria registro, chama Google Calendar, envia e-mail, faz rollback se falhar
   - `cancelarConsulta`

5. **Anamnese / Evolução**
   - `criarAnamnese`, `atualizarAnamnese`
   - `registrarEvolucao`, `atualizarEvolucao`

6. **Dosagem**
   - `criarDosagem` (calcula `data_fim_prevista` e cria `recompra` agendada)
   - `atualizarDosagem`, `desativarDosagem`

7. **Recompra**
   - `solicitarRecompraAgora` — envia e-mail imediato
   - `confirmarRecompraAgendada` — botão do e-mail futuro

8. **Chat**
   - `criarGrupo`, `adicionarParticipante`, `enviarMensagem` (dispara Pusher), `marcarComoLida`

9. **Notificações**
   - `marcarNotificacaoLida`, `marcarTodasLidas`

10. **Relatórios**
    - `gerarRelatorioPacientePDF(pacienteId)` usando `@react-pdf/renderer`

11. **Admin**
    - `listarTriagens`, `marcarTriagemVisualizada`

**Definition of Done:**
- [ ] Toda action acima implementada com Zod + role check
- [ ] Helpers criados
- [ ] `pnpm lint` e `pnpm build` passando
- [ ] Commit: `feat(fase-4): server actions e regras de negócio`

## Fase 9 — Qualidade, observabilidade e deploy

**Objetivo:** projeto em produção em `be4hope.org`.

### 9.1 Qualidade
1. Rode `pnpm lint --fix` e `pnpm format` em todo o repo.
2. Garanta que `pnpm build` passa **sem warnings críticos**.
3. Crie `.github/workflows/ci.yml` rodando `lint` + `build` em toda PR.
4. Atualize o `README.md` com: descrição, stack, setup local passo a passo, comandos.

### 9.2 Configuração da Vercel
1. Importe o repositório na Vercel.
2. Framework: **Next.js** (auto-detect).
3. Install command: `pnpm install --frozen-lockfile`
4. Build command: `pnpm build`
5. Region: **`gru1` (São Paulo)**.
6. Production branch: `main`. Preview: todas as PRs.

### 9.3 Variáveis de ambiente
1. Cadastre **todas** as variáveis do `.env.example` no painel da Vercel.
2. Separe valores por ambiente (Production / Preview).
3. Marque chaves sensíveis como **Sensitive**.
4. **🛑 Confirme com o humano** os valores de produção antes de cadastrar.

### 9.4 Banco em produção
1. Crie branch de produção no Neon.
2. Aplique migrations: `pnpm db:migrate` apontando para a connection string de produção.
3. **Não rode seed em produção.**

### 9.5 Domínio
1. Adicione `be4hope.org` na Vercel.
2. Configure DNS no registrador (registros indicados pela Vercel).
3. Adicione `www.be4hope.org` com redirect 308 para o root.
4. Aguarde SSL automático.

### 9.6 Cron jobs
- Inngest: registre o endpoint de produção `https://be4hope.org/api/inngest` no painel do Inngest.
- Caso opte por Vercel Cron, declare em `vercel.json`:
  ```json
  {
    "crons": [
      { "path": "/api/cron/verificar-validade-documentos", "schedule": "0 9 * * *" },
      { "path": "/api/cron/verificar-recompra-medicamentos", "schedule": "0 9 * * *" }
    ]
  }
  ```

### 9.7 Webhooks externos para produção
- Clerk → URL de produção
- Pusher → URL de produção
- Google OAuth redirect → `https://be4hope.org/api/auth/google/callback`

### 9.8 Observabilidade
- Habilite **Vercel Analytics** e **Speed Insights**.
- Verifique que `logs_auditoria` está sendo populado em produção (LGPD).
